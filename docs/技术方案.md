# 手账（Techo）技术方案

> 版本：v1.2
> 部署形态：**局域网自托管**
> 技术栈：Java 27 + Spring Boot 4.1 + SQLite + Thymeleaf + htmx
> 环境状态：**已在本机实测验证通过**，详见 §16

---

## 1. 项目概述

### 1.1 目标

做一个属于自己的手账网页应用，在家里的电脑上跑起来，手机连同一个 WiFi 就能打开使用，用来记录待办事项和日常事件。

### 1.2 核心范围

| 模块 | 名称 | 内容 | 特征 |
|---|---|---|---|
| 模块一 | **待办（TODO）** | 只有正文，没有标题 | 可勾选完成，完成后文字加删除线 |
| 模块二 | **记录（NOTE）** | 有标题 + 正文 | 记录各种事情 |

两个模块共用：自动时间戳、关键词搜索、按时间倒序浏览。

### 1.3 明确的非目标（本期不做）

- ❌ 多用户、注册、权限体系
- ❌ 公网访问、内网穿透、HTTPS
- ❌ 云同步、Git 备份
- ❌ 富文本 / Markdown 编辑器
- ❌ 图片、附件、语音
- ❌ 手机原生 App（用「添加到主屏幕」代替）
- ❌ 离线可写（Service Worker）

> 这些都可以作为第二期再评估，本期的目标是**先把它用起来**。

### 1.4 使用场景

1. 坐到电脑前，想起来要买牛奶 → 打开待办页 → 输入 → 回车 → 完成
2. 手机躺在沙发上，想起来一件事 → 掏出手机 → 打开手账 → 记录 → 关掉
3. 想找上周记的某件事 → 打开记录页 → 搜关键词 → 找到

**设计的第一原则：从「打开」到「保存成功」的操作步骤越少越好。** 记录类工具最大的失败原因不是功能不够，而是记录起来太麻烦，用两天就放弃了。

## 3. 技术选型

| 层次 | 选型 | 版本 | 选它的理由 |
|---|---|---|---|
| 语言 | Java | **27** | 本机已就位（`D:\Dev\jdk-27`）；技术方案原定 21，因现有环境为 27 而调整，注意 §16.3 的兼容性提示 |
| 框架 | Spring Boot | **4.1.1** | 与 Java 27 配套的当前稳定版；生态成熟，一个 jar 全包 |
| 数据库 | **SQLite** | 3.50.1 | 单文件、零运维、无需安装服务，个人用量绰绰有余 |
| JDBC 驱动 | `org.xerial:sqlite-jdbc` | 3.50.1.0 | 最主流的 SQLite JDBC 实现，**已实测可用** |
| 持久层 | **Spring JDBC (`JdbcTemplate`)** | — | 只有 2 张表级别的复杂度，写 SQL 最直接；**避开 Hibernate 对 SQLite 的方言坑** |
| 模板引擎 | Thymeleaf | 3.x | 服务端渲染，不用 Node/npm，一个 jar 全包 |
| 局部刷新 | htmx | 2.x | 一个 CDN 脚本，实现无刷新勾选/删除，不引入前端工程化 |
| 样式 | 手写 CSS | — | 页面简单，几十行即可，避免引入框架 |
| 构建 | Maven | 3.9+ | 标准、无额外配置 |
| 打包 | `spring-boot-maven-plugin` | — | 打出可直接运行的 fat jar |

### 3.1 关于持久层的重要说明

**推荐用 `JdbcTemplate` 而不是 JPA/Hibernate**，原因：

1. 数据模型极简（1 张表），JPA 的实体映射、级联、懒加载等能力用不上
2. Hibernate 官方**没有** SQLite 方言，需要额外引入 `hibernate-community-dialects`，配置容易踩坑
3. 搜索需要按条件动态拼 SQL，`JdbcTemplate` / `NamedParameterJdbcTemplate` 比 Criteria API 更直观
4. SQLite 是单写入模型，连接池配置需要特殊处理（见 §5.4），手写 JDBC 更容易控制

> 如果你更熟悉 MyBatis，也可以替换，工作量相同。**不建议用 JPA。**

## 5. 数据设计

### 5.1 表结构

只有一张表，两个模块通过 `type` 字段区分。

```sql
-- 建表语句（src/main/resources/schema.sql）

CREATE TABLE IF NOT EXISTS entry (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    type        TEXT    NOT NULL CHECK (type IN ('TODO', 'NOTE')),
    title       TEXT,                                   -- TODO 为 NULL，NOTE 有值
    body        TEXT    NOT NULL DEFAULT '',
    done        INTEGER NOT NULL DEFAULT 0
                        CHECK (done IN (0, 1)),         -- 0=未完成 1=已完成
    done_at     INTEGER,                                -- 完成时刻 (epoch millis, UTC)
    created_at  INTEGER NOT NULL,                       -- 创建时刻 (epoch millis, UTC)
    updated_at  INTEGER NOT NULL,                       -- 最后修改时刻 (epoch millis, UTC)
    deleted_at  INTEGER,                                -- 非 NULL = 在回收站里（软删除）
    parent_id   INTEGER,                                -- 非 NULL = 这是某条待办的子目录
    sort_order  INTEGER NOT NULL DEFAULT 0              -- 同一父级下子目录的排序
);

-- 列表主查询：按模块 + 时间倒序
CREATE INDEX IF NOT EXISTS idx_entry_type_created
    ON entry (type, created_at DESC);

-- 待办筛选：按模块 + 完成状态 + 时间倒序
CREATE INDEX IF NOT EXISTS idx_entry_type_done
    ON entry (type, done, created_at DESC);

-- ⚠️ idx_entry_deleted 和 idx_entry_parent 这两个索引**故意不写在这里**，
-- 原因见下方说明。

-- 应用设置。目前只用来存登录密码的 BCrypt 哈希
CREATE TABLE IF NOT EXISTS app_setting (
    key         TEXT    PRIMARY KEY,
    value       TEXT    NOT NULL,
    updated_at  INTEGER NOT NULL
);
```

> **子目录为什么复用 entry 表？**
>
> `parent_id` 非 NULL 就是子目录。这样回收站、导出、时间戳、软删除**全部自动共享**，
> 不用为子目录再写一套平行的表和逻辑。代价只是顶层查询要多加一个
> `parent_id IS NULL` 条件。详见 §16.13。

> **为什么 `idx_entry_deleted` 不在 `schema.sql` 里？**
>
> `schema.sql` 由 Spring 在启动早期执行，而给老库补 `deleted_at` 列的迁移器
> （`SchemaMigration`）是 `ApplicationRunner`，跑得更晚。如果在这里建索引，
> **老库会先建索引、后加列**，直接报 `no such column: deleted_at` 让应用启动失败。
>
> 该索引改由 `SchemaMigration` 在补完列之后创建。
> 这个坑只有用**老结构的数据库**启动才会暴露，用新建的空库测永远发现不了。

### 5.2 字段说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER | 主键，自增 |
| `type` | TEXT | `'TODO'` 或 `'NOTE'`，决定属于哪个模块 |
| `title` | TEXT | 标题。**待办恒为 NULL**，记录必填 |
| `body` | TEXT | 正文。待办里就是待办内容本身 |
| `done` | INTEGER | 0/1。**仅待办使用**，记录恒为 0 |
| `done_at` | INTEGER | 完成时间戳，未完成时为 NULL；取消完成时置回 NULL |
| `created_at` | INTEGER | 创建时间戳，**由服务端生成，用户不可改** |
| `updated_at` | INTEGER | 每次修改自动更新 |

### 5.3 时间与时区约定（重要）

这是最容易埋雷的地方，必须统一：

| 环节 | 约定 |
|---|---|
| **存储** | `epoch millis`（UTC 毫秒数），`INTEGER` 类型 |
| **Java 类型** | `java.time.Instant`（**不要用** `java.util.Date` / `LocalDateTime`） |
| **服务端生成** | `Instant.now()`，**绝不用数据库的 `NOW()`** |
| **时区转换** | 只在**展示时**转成 `Asia/Shanghai` |
| **JSON 传输** | ISO-8601 字符串，如 `2026-03-05T02:15:30Z` |
| **前端展示** | 统一格式化为 `2026-03-05 10:15`（本地时区） |

**为什么用 epoch millis 而不是字符串？** 字符串存时间无法正确排序、无法跨时区转换、无法做范围查询，改起来极其痛苦。

**为什么时区转换只放展示层？** 如果存储时就转成本地时间，以后换时区或做统计（比如「本月记录了多少条」）会全部错乱。

服务端固定时区配置：

```yaml
spring:
  jackson:
    time-zone: Asia/Shanghai
    date-format: yyyy-MM-dd'T'HH:mm:ssXXX
```

### 5.4 SQLite 配置要点（已实测验证）

实测结论（详见 §16.3）：`journal_mode` 会**持久化到数据库文件**，但 `busy_timeout` / `synchronous` / `foreign_keys` **都是连接级设置**，每条新建连接都要重新应用。

**因此 PRAGMA 一律写在 JDBC URL 里** —— 连接池每次建连都会自动带上，不会漏：

```yaml
# application.yml
spring:
  datasource:
    # 必须写成单行并加引号。用 YAML 的 >- 折叠写法会把换行变成空格，
    # 导致 URL 里多出一个空格而连接失败。
    url: "jdbc:sqlite:D:/DSHWorkSpace/Techo/data/journal.db?journal_mode=WAL&busy_timeout=5000&synchronous=NORMAL&foreign_keys=true"
    driver-class-name: org.sqlite.JDBC
    hikari:
      maximum-pool-size: 1
      pool-name: techo-pool
  sql:
    init:
      mode: always
      schema-locations: classpath:schema.sql
```

**连接池必须配成单连接：** `maximum-pool-size: 1`。

> SQLite 同一时刻只允许**一个写事务**。默认连接池有 10 个连接，并发写入时会频繁抛出 `SQLITE_BUSY`。个人应用并发极低，**池大小设为 1 是最简单且绝对正确的选择**。

#### ⚠️ 三个必须避开的坑（均为实测结论）

| # | 坑 | 实测表现 | 正确做法 |
|---|---|---|---|
| 1 | **一条 `execute` 塞多条 PRAGMA** | `s.execute("PRAGMA a; PRAGMA b; PRAGMA c;")` **不抛任何异常**，但**只有第一条生效**，后面静默失效 | 逐条执行，或直接写进 URL |
| 2 | **在 `@PostConstruct` / `ApplicationRunner` 里执行一次 PRAGMA** | 只对当时那一条连接有效；连接池重建连接后设置全部丢失 | 写进 URL，让每次建连都应用 |
| 3 | **数据库用相对路径** | 换个目录启动就连到另一个空库，表现为「数据全丢」 | 配置里写绝对路径 |

实测数据对照：

| 方式 | journal_mode | busy_timeout | synchronous |
|---|---|---|---|
| **JDBC URL 参数** | wal ✅ | 5000 ✅ | 1 (NORMAL) ✅ |
| 什么都不设（SQLite/xerial 默认） | delete ❌ | 3000 | 2 (FULL) |
| 建连后逐条显式 PRAGMA | wal ✅ | 5000 ✅ | 1 ✅ |
| 一条 `execute` 塞多条 PRAGMA | wal ✅ | **3000 ❌** | **2 ❌** |

> 最后一行是最危险的：**看起来成功了，实际静默失效**，没有任何异常或日志提示。

**验证方式：** 应用提供 `GET /api/health`，启动后访问即可确认 `journalMode` 是否为 `wal`。若返回 `delete`，说明配置没生效，必须排查。

### 5.5 数据量评估

| 条目数 | 数据库大小（估） | 搜索耗时（LIKE） |
|---|---|---|
| 1,000 | ~200 KB | < 5 ms |
| 10,000 | ~2 MB | < 20 ms |
| 50,000 | ~10 MB | < 100 ms |

个人手账写到 5 万条需要很多年。**结论：`LIKE` 搜索足够，本期不引入全文索引。**

## 7. 核心逻辑设计

### 7.1 待办划线（FR-02）

**关键设计决定：不存 `~~文字~~`，存布尔状态。**

| 方案 | 评价 |
|---|---|
| 把删除线存进正文（`~~买牛奶~~`） | ❌ 手机上打不出 `~~`；判断状态要解析文本；搜索会搜到符号 |
| **存 `done` 布尔字段，前端渲染删除线** | ✅ **采用** |

前端渲染：

```css
.todo-item.done .todo-body {
    text-decoration: line-through;
    opacity: 0.5;
}
```

交互流程（htmx）：

```html
<button hx-patch="/api/entries/128/done"
        hx-vals='{"done": true}'
        hx-target="#todo-128"
        hx-swap="outerHTML">
```

**移动端要点：** 手机上无法使用 `Ctrl+D` 之类的快捷键，所以**必须有一个明确的、足够大的可点击区域**来切换状态（整行点击或一个大号复选框），点击目标不小于 44×44 px。

### 7.2 自动记录时间（FR-04）

在 `EntryService` 中集中处理，**不允许由 Controller 或前端传入**：

```java
public Entry create(EntryType type, String title, String body) {
    Instant now = Instant.now();
    Entry e = new Entry();
    e.setType(type);
    e.setTitle(type == EntryType.NOTE ? title : null);
    e.setBody(body);
    e.setDone(false);
    e.setCreatedAt(now);
    e.setUpdatedAt(now);
    return repository.insert(e);   // 插入后回填自增 id
}

public void setDone(long id, boolean done) {
    Instant now = Instant.now();
    repository.updateDone(id, done, done ? now : null, now);
}
```

| 字段 | 什么时候写 |
|---|---|
| `created_at` | 只在 INSERT 时写一次，之后永不修改 |
| `updated_at` | 每次 INSERT / UPDATE 都刷新 |
| `done_at` | 勾选完成时写入当前时间；取消完成时置为 NULL |

> **安全考虑**：时间戳如果允许前端传，前端时钟不准或被篡改就会写出错误日期。**服务端生成是唯一正确做法。**

### 7.3 搜索（FR-05）

本期使用 `LIKE` 模糊匹配，同时匹配标题和正文。

**SQL（带关键词）：**

```sql
SELECT id, type, title, body, done, done_at, created_at, updated_at
FROM entry
WHERE type = :type
  AND (title LIKE :kw ESCAPE '\' OR body LIKE :kw ESCAPE '\')
  AND (:status = 'all' OR done = :doneFlag)
ORDER BY created_at DESC, id DESC
LIMIT :size OFFSET :offset;
```

配套的 COUNT 查询用于分页总数。

**三个必须注意的实现细节：**

1. **转义通配符。** 用户输入的 `%` 和 `_` 在 `LIKE` 中是通配符。若用户搜索「50%」，不转义会匹配到所有含「50」的内容。必须先转义：
   ```java
   String escaped = kw.replace("\\", "\\\\")
                      .replace("%", "\\%")
                      .replace("_", "\\_");
   String pattern = "%" + escaped + "%";
   ```
2. **动态拼 SQL 要用参数绑定。** 用 `NamedParameterJdbcTemplate` 按条件拼接 `WHERE` 子句，**值一律走 `:param` 占位符**，绝不字符串拼接，防止 SQL 注入。
3. **大小写。** SQLite 的 `LIKE` 对 ASCII 字母默认不区分大小写，对中文无影响（中文没有大小写）。

**搜索范围：** 两个模块分别搜。待办页搜待办，记录页搜记录。不提供跨模块合并搜索，保持概念清晰。

### 7.4 分页（FR-10）

采用**页码分页**（`LIMIT / OFFSET`），默认每页 20 条。

- 待办列表通常不长，可以先「加载更多」按钮，够用就不做复杂分页控件
- 记录列表条目多，用页码或无限滚动

> `OFFSET` 在超大偏移时性能会下降，但 5 万条以内无感知，不需要游标分页。

### 7.5 编辑与删除

- **编辑**：点击条目展开编辑区，保存时只更新 `title` / `body` / `updated_at`，**不动 `created_at`**
- **删除**：二次确认（`confirm()` 或 inline 二次点击），成功后从列表移除
- 本期为**硬删除**。数据安全由导出功能兜底（见 §10）

|---|---|
| 新增待办 | 输入框 + 回车即提交，**不要强制点按钮** |
| 新增记录 | 标题框、正文框，`Ctrl+Enter` 提交 |

### 8.3 移动端适配（关键）

这几条直接决定手机上好用不好用：

1. **必须有 viewport meta**，否则手机上显示的是缩小版桌面页面：
   ```html
   <meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
   ```
2. **iOS 键盘遮挡输入框。** 输入框获得焦点时页面不会自动滚动。处理方式：聚焦时 `scrollIntoView({block: 'center'})`，或把输入区做成 sticky 定位。
3. **点击区域 ≥ 44×44 px。** 手指没那么精确，小按钮点不中会让人烦躁。
4. **输入框字号 ≥ 16px。** iOS Safari 在字号小于 16px 的输入框聚焦时会自动放大页面，体验很差。
5. **链接/按钮加 `touch-action: manipulation`**，去掉 300ms 点击延迟。
6. **保留换行**：正文用 `white-space: pre-wrap`，用户在待办里换行不会被吃掉。
7. **`<html lang="zh-CN">`**，保证中文字体渲染正常。

**响应式断点：**

```css
/* 手机优先 */
.container { max-width: 720px; margin: 0 auto; padding: 12px; }

@media (min-width: 768px) {
  /* 平板/桌面：稍微加大间距，不需要复杂布局变化 */
}
```

因为内容本身就是单列流式布局，**手机和电脑可以共用同一套布局**，这是最省事也最不容易出问题的做法。

### 8.4 添加到主屏幕

在 `static/` 下放一个 `manifest.json`：

```json
{
  "name": "Techo 手账",
  "short_name": "Techo",
  "start_url": "/todo",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#3b82f6",
  "icons": [{ "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" }]

```

| 平台 | 行为 |
|---|---|
| iOS Safari | 「添加到主屏幕」通过 HTTP 也可用，表现为一个网页快捷方式 |
| Android Chrome | 「添加到主屏幕」快捷方式可用；完整的 PWA 安装提示需要 HTTPS |

> 局域网是 HTTP，**完整的 PWA 安装能力不可用**，但快捷方式足够达到「像 App 一样打开」的效果。本期接受这个限制。

## 9. 安全设计

局域网不等于安全——同 WiFi 下可能有家人、访客、甚至被蹭网的陌生人。

| 措施 | 说明 | 状态 |
|---|---|---|
| **简单密码登录** | 单个密码 + Session，BCrypt 哈希**存在数据库**里（不是配置文件） | ✅ 已实现，但**当前配置为关闭**，见下方说明 |
| **绑定内网地址** | `server.address=0.0.0.0` 仅监听内网；确认路由器未做端口映射到外网 | ✅ |
| **防火墙按网段限制** | `-RemoteAddress 192.168.1.0/24`，只允许家里网段的设备连入 | ⬜ 待你执行 |
| **SQL 参数绑定** | 所有查询用占位符，杜绝拼接 | ✅ |
| **输入长度限制** | 标题 ≤ 200 字符，正文 ≤ 20000 字符 | ✅ |
| **XSS 防护** | Thymeleaf 默认转义；全部使用 `th:text`，没有一处 `th:utext` | ✅ |
| **CSRF** | 没有引入 token，靠 `SameSite=Lax` 会话 Cookie 挡住跨站 POST | ✅ 够用 |
| **登录失败限制** | 同一来源连续错 5 次锁 5 分钟 | ✅ 随登录功能一起实现 |

#### ⚠️ 当前的实际安全边界

`techo.auth.enabled` 设为 **`false`**（单人使用，不想每次登录）。

这意味着：

> **同一个 WiFi 下的任何设备，打开 `http://本机IP:8080` 都能直接看到全部内容。**

此时代替密码起作用的是**防火墙规则的网段限制**：

```powershell
New-NetFirewallRule -DisplayName "Techo 8080" -Direction Inbound -Protocol TCP `
    -LocalPort 8080 -Action Allow -Profile Any -RemoteAddress 192.168.1.0/24
```

`-RemoteAddress` 才是真正的边界，**不依赖 Windows 对网络是「公用」还是「专用」的判定**。

**残余风险（诚实说明）：** 如果这台电脑以后连到别的也用 `192.168.1.x` 网段的网络
（很多家用路由器默认就是这个网段，酒店、咖啡馆常见），这条规则在那边同样生效。

**想开回登录**：把 `techo.auth.enabled` 改成 `true` 即可，登录相关代码全部保留，
之前设过的密码也还在数据库里（`app_setting` 表的 `auth.password-hash`）。

#### 密码存储

早期设计打算把 BCrypt 哈希写在配置文件里：

```yaml
techo:
  auth:
    password-hash: "$2a$10$...."   # 这是原计划，最终没有采用
```

实际实现放在了数据库的 `app_setting` 表里。好处有两个：密文不落在明文配置文件里；
「首次设置密码」可以做成网页流程，不需要用户手工生成哈希再填进 yml。

> 无论存在哪里，**都不能明文存密码**。即使只有一个用户，明文文件一旦泄露
> （比如误发截图、误上传），后果是全量数据暴露。

## 10. 备份与恢复（简版）

本期无 Git、无云。数据在**一台机器的两个文件**里，风险集中，因此这一步不能省。

### 10.1 三层策略

| 层次 | 做法 | 频率 |
|---|---|---|
| 应用内导出 | 应用提供「导出为 JSON / Markdown」按钮，下载到手机或电脑 | 按需 |
| 本地快照 | 定时任务执行 `VACUUM INTO` 生成一致性快照，滚动保留最近 30 份 | 每天 |
| 异地副本 | 把快照目录复制到移动硬盘 / U 盘 / 另一台电脑 | 每周 |

### 10.2 一致性快照（不能直接复制文件）

SQLite 开启 WAL 后存在 `journal.db-wal` 附属文件，**直接在运行中复制 `journal.db` 可能拿到不完整的半截数据**。正确做法：

```sql
VACUUM INTO './backup/journal-20260305.db';
```

这会生成一个**完整且一致**的独立数据库文件，是最简单可靠的备份方式。

### 10.3 恢复演练（别省这一步）

**没验证过的备份等于没有备份。** 上线后要做一次演练：

1. 把 `backup/journal-20260305.db` 复制到一个空目录
2. 改配置指向它，启动应用
3. 确认所有条目都在、都能搜到

演练通过了，才算真的有备份。

### 10.4 导出格式

| 格式 | 用途 |
|---|---|
| **JSON**（每行一条，JSONL） | 可重新导入，也可用其他程序处理 |
| **Markdown** | 人可读，按日期分文件，即使不用这个程序也能翻阅 |

**导出功能的价值不只是备份，更是「数据不被锁死在这个程序里」。** 建议优先实现。

## 11. 部署方案（局域网）

### 11.1 打包

```bash
mvn clean package -DskipTests
# 产物：target/techo-1.0.0.jar
```

### 11.2 启动

```bash
java -Dfile.encoding=UTF-8 --enable-native-access=ALL-UNNAMED -jar techo-1.0.0.jar
```

> `--enable-native-access=ALL-UNNAMED` 是 **Java 27 下必须加的参数**。sqlite-jdbc 通过 JNI 加载本地库，从 JDK 24 起这类调用会产生警告（`A restricted method in java.lang.System has been called`），并明确提示「**未来版本将直接阻止**」。现在加上这个参数即可消除警告并为将来做好准备。详见 §16.3。

`application.yml` 关键配置：

```yaml
server:
  port: 8080
  address: 0.0.0.0        # 监听所有网卡，手机才能访问

spring:
  datasource:
    url: jdbc:sqlite:./data/journal.db   # 相对启动目录，建议改用绝对路径
  thymeleaf:
    cache: false          # 开发期关闭；生产改为 true

logging:
  file:
    name: ./logs/techo.log
```

> **数据库路径建议用绝对路径**，如 `jdbc:sqlite:D:/Techo/data/journal.db`。否则换个目录启动就会「数据全没了」——其实只是连到了另一个新库。

### 11.3 查本机内网 IP

```powershell
ipconfig | Select-String "IPv4"
# 例：IPv4 地址 . . . . . . . . . . . . : 192.168.1.5
```

### 11.4 放行防火墙

Windows 默认会拦截入站连接，需要放行 8080 端口（**管理员权限**）：

```powershell
New-NetFirewallRule -DisplayName "Techo 8080" `
  -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow `
  -Profile Private
```

注意 `-Profile Private`：只对「专用网络」生效，避免在公共 WiFi 下暴露。

### 11.5 手机访问

1. 手机连接**与电脑相同的 WiFi**
2. 浏览器打开 `http://192.168.1.5:8080`
3. 加入书签，或「添加到主屏幕」

### 11.6 常驻运行

| 方式 | 适用 |
|---|---|
| 前台 `java -jar` | 临时试用 |
| **WinSW / NSSM 注册为 Windows 服务** | ✅ 推荐，开机自启、崩溃自动重启 |
| 计划任务 | 备选 |

同时需要：

- **电源设置改为「从不睡眠」**，否则电脑一睡手机就连不上
- 关掉「快速启动」等可能导致网络中断的设置
- 建议给这台机器配 UPS（可选）

### 11.7 故障排查表

| 现象 | 排查方向 |
|---|---|
| 电脑上能开，手机打不开 | 防火墙未放行 / 监听地址不是 `0.0.0.0` / 手机不在同一 WiFi |
| 手机能 ping 通电脑但打不开网页 | **路由器开启了 AP 隔离**（访客网络常见），需在路由器关闭 |
| IP 变了连不上 | 路由器里给电脑**绑定静态 IP / DHCP 保留** |
| 页面样式全乱 | 静态资源路径错误，检查 `static/` 目录结构 |
| 中文乱码 | 启动参数缺 `-Dfile.encoding=UTF-8` |
| 提示 `SQLITE_BUSY` | 连接池没设成 1，或 `busy_timeout` 未生效 |
| `/api/health` 里 `journalMode` 不是 `wal` | PRAGMA 没写进 JDBC URL，或被「一条 execute 塞多条」吞掉了（见 §5.4） |
| 应用启动失败，提示 URL 非法 | `application.yml` 里数据源 URL 用了 `>-` 折叠写法，换行被折成了空格 |
| 换目录启动后「数据全丢」 | 数据库用了相对路径，实际连到了另一个空库 |
| 服务启动后立刻停止 | jar 路径不对或 JDK 路径变了，看 `logs\service\techo.wrapper.log` |

### 11.8 服务化部署（已准备好，需你执行）

`service/` 目录里已经备好完整的 Windows 服务方案：

| 文件 | 作用 |
|---|---|
| `techo.exe` | WinSW 2.12.0 服务包装器（.NET Framework 4.6.1 版，640 KB，Win11 自带依赖） |
| `techo.xml` | 服务配置：自动启动、崩溃分次重启、日志轮转 |
| `install-service.cmd` | **右键以管理员身份运行**即可完成安装 |
| `uninstall-service.cmd` | 卸载 |
| `README.md` | 完整的部署说明（含防火墙与静态 IP） |

**为什么选 WinSW 而不是 NSSM 或计划任务：**

- NSSM 已多年不更新
- 计划任务做不出「崩溃自动重启 + 延迟递增 + 日志轮转」
- WinSW 用 XML 声明式配置，`install` / `uninstall` 语义清晰

**选 .NET Framework 4.6.1 版而不是自包含的 `WinSW-x64.exe`**：前者 640 KB，后者 18 MB。
Windows 11 自带 .NET Framework 4.6.1，没有额外依赖。

> ⚠️ **XML 注释里不能出现两个连续的连字符。** 配置里要在注释中提到
> `enable-native-access` 这个参数时踩了这个坑——WinSW 直接报
> `XML 注释中不能包含"--"` 并拒绝加载。这个错误是**靠实际让 WinSW 解析一次配置才发现的**，
> 光看文件是看不出来的。

剩下需要你做的两件事（都需要管理员权限或路由器后台）：

1. 运行 `install-service.cmd`
2. 防火墙放行 + 路由器绑定静态 IP（见 `service/README.md` 第三、四节）

### 16.3 ⚠️ 两个必须知道的发现

#### （1）SQLite 默认不是 WAL 模式

实测 `/probe` 返回 `"journalMode":"delete"` —— 这是 SQLite 的**默认日志模式，不是 WAL**。

这直接印证了 §5.4 的必要性：**必须显式开启 WAL**，否则手机和电脑同时访问时会出现读写互相阻塞。**这不是优化项，是必做项。**

> 📌 后续通过 `PragmaTest` 探针进一步确认了正确做法：**把 PRAGMA 写进 JDBC URL**，而不是在初始化类里执行一次。原因和三个坑详见 §5.4。

#### （2）Java 27 下 sqlite-jdbc 会触发受限原生方法警告

启动日志中出现：

```
WARNING: A restricted method in java.lang.System has been called
WARNING: java.lang.System::load has been called by org.sqlite.SQLiteJDBCLoader
WARNING: Use --enable-native-access=ALL-UNNAMED to avoid a warning
WARNING: Restricted methods will be blocked in a future release
         unless native access is enabled
```

sqlite-jdbc 通过 JNI 加载本地库，从 JDK 24 起这类调用被标记为「受限」，**当前只是警告，不影响运行**，但官方明确表示未来版本会变成硬性阻止。对策：

| 方案 | 说明 |
|---|---|
| **加启动参数**（推荐） | `--enable-native-access=ALL-UNNAMED`，见 §11.2 |
| IDEA 运行 | Run Configuration → VM options 填同一个参数 |
| 回退 JDK | 若不想处理这类新版本适配问题，可换回 JDK 21 LTS + Spring Boot 3.5.x，兼容性最稳妥（需重新下载 JDK） |

#### 🐞 发现并修复的 bug

**问题：** 页面控制器抛出的 `BizException` 返回了 **HTTP 500**，而不是预期的 400。

**根因：** `GlobalExceptionHandler` 用了 `assignableTypes = EntryApiController.class` 限定作用范围（这是 M2 刻意做的，避免页面异常返回 JSON），结果 `TodoController` / `NotesController` 的异常**没有任何处理器接管**，直接落到 Spring 默认的 500 错误页。

**修复分两步：**

1. 新增 `PageExceptionHandler`，限定作用于两个页面控制器，返回 **400 + 纯文本**错误消息
2. 新增 `static/js/app.js`。这一步不能省 —— **htmx 默认不会把 4xx/5xx 的响应内容替换进页面**（配置 `responseHandling` 里 `[45]..` 是 `swap:false`），所以就算服务端返回了可读消息，用户看到的仍然是「点了没反应」。`app.js` 监听 `htmx:responseError` / `sendError` / `timeout`，把消息显示成一个提示条

### 16.11 内存占用实测与调优

**测量方法：** 启动应用 → 发 30 次请求 → 用 `Get-Process` 读 `WorkingSet64`（工作集，就是任务管理器里显示的「内存」）和 `PrivateMemorySize64`。

| JVM 参数 | 工作集 | 私有字节 | 线程数 |
|---|---|---|---|
| 默认（无任何参数） | 386 MB | 461 MB | 76 |
| `-Xms32m -Xmx192m` | 184 MB | 258 MB | 77 |
| 再加 `-XX:+UseSerialGC` | 160 MB | 152 MB | 43 |
| **再加 `-XX:ActiveProcessorCount=2`** | **151 MB** | **143 MB** | **36** |
| 再加 `-XX:MaxMetaspaceSize=128m` | 169 MB | 163 MB | 36 |

> 最后一行反而**变差**了（169 vs 151），所以限制元空间这个参数**没有采用**。
> 这是实测推翻直觉的例子：想当然地「限制更多资源」不一定更好。

**最终采用：**

```
-Xms32m -Xmx192m -XX:+UseSerialGC -XX:ActiveProcessorCount=2
```

**三条参数各自为什么有效：**

| 参数 | 作用 |
|---|---|
| `-Xmx192m` | 默认堆上限由 JVM 按物理内存的 1/4 自动计算，**本机算出来是 3.8 GB**。个人手账根本用不到 |
| `-XX:+UseSerialGC` | 单用户应用没有吞吐压力。并行 / 并发 GC 会为每个核开线程，实测线程数从 77 降到 43 |
| `-XX:ActiveProcessorCount=2` | 本机 32 个逻辑核，JVM 会按核数开 GC 线程和 ForkJoinPool。告诉它只有 2 核，线程数进一步降到 36 |

**调优后全量功能复测：** 11 项（登录 → 两模块增改查 → 搜索 → 勾选 → 备份 → 导出 → 回收站 → 健康检查）**全部通过，日志无 WARN / ERROR**。

#### ⚠️ 一个必须澄清的误解

**`-Xmx` 是「上限」不是「预占用」。**

默认 3.8 GB 的堆上限**不代表应用会占 3.8 GB** —— 实测默认配置下工作集是 386 MB。
JVM 只按需向操作系统要内存，不会一上来就把 3.8 GB 全占了。

那为什么还要调低？因为：

1. 堆上限低时，JVM 的 GC 策略会不同（更早回收、更少预留）
2. `-XX:+UseSerialGC` 和 `-XX:ActiveProcessorCount` 省掉的是**线程开销**，这部分是实打实的常驻内存
3. 上限低也让内存问题暴露得更早，而不是等到某天悄悄涨到 3 GB

> **对比参考：** IntelliJ IDEA 本身通常占 1.5 ~ 3 GB 内存，是 Techo 应用的 **10 倍以上**。
> 关掉 IDEA 只跑应用，省下来的远比应用占的多。

### 16.13 待办子目录验证报告

#### 交互定义
| 位置 | 手势 | 结果 |
|---|---|---|
| 父待办 | **点击待办本身** | 展开 / 收起子目录 |
| 父待办 | 左划 | 露出绿色 `↵`，点击在子目录**末尾**加一条 |
| 子目录 | 左划 | 露出绿色 `↵` + 蓝色 `✎` + 红色 `✕` |

三个动作的含义：

- **`↵` 加一条** —— 在**这一条下方**插入
- **`✎` 改文字** —— 就地弹出输入框，带原文字，回车保存、Esc 取消
- **`✕` 删除** —— 删掉这一条（进回收站）

点 `↵` 或 `✎` 之后会**就地弹出一个输入框**（不是弹窗、不是跳页），
打完按回车保存。这样不会产生空记录，也和「回车」这个图标的语义一致。

同一时刻只允许一个输入框打开 —— 点另一个动作会自动收起前一个，
避免两个框叠在一起。按 Esc 取消时会把编辑框**还原成原始文字**，
不然下次打开还留着上次没保存的内容。

#### 数据模型：子目录复用 entry 表

没有新建 `subtask` 表，而是给 `entry` 加了两个列：

| 列 | 含义 |
|---|---|
| `parent_id` | 非 NULL 即表示这是某条待办的子目录 |
| `sort_order` | 同一父级下的排序 |

**这么做的收益**：回收站、导出、时间戳、软删除、勾选逻辑**全部自动共享**，
不需要为子目录再写一套平行的仓储和服务。代价只是顶层查询要多加一个
`parent_id IS NULL`。

实测确认这个选择是对的 —— 回收站里子目录自动出现（还带了「属于「周末采购」」的归属提示），
导出里自动变成嵌套列表，都是**没有专门写代码**就得到的。

**排序策略**：整数排序号，「插到某条下面」= 把它后面的整体 +1，再把新的放进空位。
子目录数量很少，这个做法的代价可以忽略，但读起来比分数排序直观得多。

#### 🐞 发现并修复的 bug

**问题：** 空内容提交返回 **500「服务器内部错误」**，而不是预期的 204。

**根因：** `PageExceptionHandler` 里的兜底 `@ExceptionHandler(Exception.class)`
把 `ResponseStatusException` 也一起吞了 —— 而页面控制器正是用
`throw new ResponseStatusException(NO_CONTENT)` 表达「空内容，什么都不做」。

**关键点：** Spring 自带的 `ResponseStatusExceptionResolver` 排在
`ExceptionHandlerExceptionResolver` **之后**。所以只要存在一个 catch-all 的
`@ExceptionHandler(Exception.class)`，自带解析器就**永远没有机会执行**。

**修复：** 显式加一个 `@ExceptionHandler(ResponseStatusException.class)`。

> 这个 bug 是 **M3 引入的**（那次为了修页面异常返回 JSON 的问题加了 catch-all），
> 但当时测试里只验了 `BizException` 那条路径，没验 `ResponseStatusException`，
> 所以一直潜伏到这次加子目录才被翻出来。
>
> 教训：**加了 catch-all 异常处理器之后，必须回头把所有「本来由框架处理」的异常路径重测一遍。**

**问题 2（加铅笔按钮时发现的）：** `DELETE /todo/subtasks/{父待办id}` 返回 **500** 而不是 400。

**根因：** 控制器先 `service.get(id)` 再取 `subtask.getParentId()` 拆箱成 `long` ——
而父待办的 `parent_id` 是 `null`，直接拆箱会 **NPE**。校验（`requireSubtask`）发生在**拆箱之后**，
所以永远轮不到它抛 400。

**修复：** 加一个 `service.getSubtask(id)`，让调用方**先校验再拆箱**。

> 同一组端点里 PUT 和 PATCH 都没问题，因为它们第一步就把校验放在了服务方法内部。
> 只有 DELETE 因为在返回徽标前需要先拿到 `parentId`，把顺序写反了。
>
> 教训：**「先校验还是先取值」的顺序，在 `null` 会参与拆箱时不是风格问题，是正确性问题。**

**问题 3（用户实际使用后反馈）：电脑上鼠标一移上去整行就左移，导致没法勾选划线。**

**根因：** 桌面端最初用
`@media (hover: hover) and (pointer: fine) { .row-clip:hover .row-slide { transform: translateX(-60px) } }`
做「悬停揭示动作按钮」。但行内容整体左移后，**最左边的勾选圈被推出 `overflow:hidden` 的裁剪区** ——
鼠标还没移到它上面，它就先跑掉了。子目录位移更大（156px），更严重。

**修复：** 放弃「位移式揭示」，改成**同一份 DOM、两套排布**：

| 设备 | 排布 |
|---|---|
| 鼠标（默认） | `.row-clip` 是 flex 容器，`.row-actions` 作为行内项**直接排在行尾，始终可见** |
| 触屏（`pointer: coarse`） | `.row-actions` 绝对定位到行后，被行内容盖住，靠左划揭示 |

桌面端的按钮默认是**中性灰、悬停才上色** —— 不然每行都挂着一排红绿按钮太扎眼。

**默认走「桌面」那套**，只有明确检测到触屏才切到左划模式。
这样万一媒体查询没命中，用户看到的是**可用的按钮**，而不是一个用不了的手势 —— 优雅降级。

> 教训：**「悬停时移动被悬停的元素（或其内容）」是个陷阱。**
> 元素一移动，鼠标下的目标就变了，轻则闪烁，重则像这次一样根本点不中。
> 要揭示额外内容，优先考虑**不改变已有元素位置**的做法。

#### 桌面端按钮重排：为什么要用 `display: contents`

改完位移问题后，桌面端的按钮顺序是 `勾选 → 正文 → 编辑 → 删除 → 加子目录` ——
「加子目录」跑到了删除后面，因为它在 DOM 里是行的**兄弟节点**：

```
.row-clip                       ← flex 容器（桌面）
  ├── .row-slide                ← 嵌套的 flex 容器
  │     ├── .todo-check
  │     ├── .todo-text
  │     ├── .todo-icon          （编辑）
  │     └── .todo-delete        （删除）
  └── .row-actions
        └── .swipe-add          （加子目录）
```

`.row-actions` 和 `.todo-icon` **分属两个 flex 上下文**，`order` 够不着对方，
所以光写 CSS 是排不动的。

**解法：桌面端给 `.row-slide` 加 `display: contents`**，这一层被「解除」，
它的子元素直接变成 `.row-clip` 的 flex 子项，于是全部按钮进了同一个上下文：

```
.row-clip                       ← display: flex
  ├── .todo-check    order: 1
  ├── .todo-text     order: 2
  ├── .row-actions   order: 3   （加子目录）
  ├── .todo-icon     order: 4   （编辑）
  └── .todo-delete   order: 5   （删除）
```

**关键点：这次重排只加在默认（桌面）分支里。** 触屏分支
（`@media (pointer: coarse)`）会把 `display` 还原成 `flex`、把 `order` 全部重置为 `0`，
**手机上的左划行为和按钮顺序一个字节都没变**。

`display: contents` 需要各子元素自己带 `flex` 属性（因为父层的 flex 设置随该层一起消失了）。
好在这套代码从「`.row-slide` 是 flex 容器」的时期起，`flex: 0 0 auto` / `flex: 1 1 auto`
就一直写在各个子元素上，所以不用额外补。

> **优雅降级：** 如果浏览器不支持 `display: contents`，`.row-slide` 会保持 `flex`，
> 结果是按钮顺序退回改动前 —— 只降级，不损坏。

#### 视觉验证：终于能"看见"页面了

**问题：** 这个项目从头到尾都缺一环 —— 能验证 HTML、CSS、JS 都正确送达，
却**从来没能真正看一眼渲染出来的样子**。于是像「按钮贴在顶部没有居中」
「父待办用 `×` 而子目录用 `✕` 导致粗细不一」这类问题，只能等你肉眼发现再回头改。

**办法：用 Windows 自带的 Edge 跑无头截图。**

```powershell
msedge.exe --headless=new --disable-gpu --no-sandbox `
  --force-device-scale-factor=2 `
  --user-data-dir=<临时目录> `
  --virtual-time-budget=4000 `
  --window-size=900,620 `
  --screenshot=<输出.png> http://127.0.0.1:8080/todo
```

几个要点：

| 参数 | 作用 |
|---|---|
| `--headless=new` | 新版无头模式，旧版 `--headless` 在这个环境里会崩 |
| `--no-sandbox` | 不加会以退出码 `0x80000003` 崩溃 |
| `--force-device-scale-factor=2` | 2 倍渲染，方便看清像素级差异 |
| `--virtual-time-budget=4000` | 等页面和 htmx 都渲染完再截 |
| `--user-data-dir` | 指定临时目录，避免和正在运行的 Edge 打架 |

**注意：这个命令需要放宽沙箱权限。** 普通沙箱下 Edge 会以 `0x80000003` 崩溃
（浏览器需要访问工作区外的临时目录和注册表）。

**验证效果**：统一字形之后，用 Pillow 逐像素量三个图标的包围盒，
父待办和子目录**逐项完全相同**：

| 图标 | 父待办 | 子目录 |
|---|---|---|
| 加子目录 `↵` | 15×19 | 15×19 |
| 编辑铅笔 | 23×23 | 23×23 |
| 删除 `✕` | 26×26 | 26×26 |

> 这类「看起来差不多但实际不一样」的问题，**肉眼很容易放过，量一下立刻现形**。
> 铅笔的差异就来自 `stroke-width` 一个 `1.7` 一个 `1.8`。

**局限：** 无头浏览器报告的是 `pointer: fine`，所以**只能验证电脑端布局**，
验证不了触屏分支（`pointer: coarse`）。手机上的左划仍然只能真机试。
